# Жизненный цикл одного правила — только DEMO

Локальный прототип разовой условной покупки. В базовом DEMO события, активы, цены и результаты синтетические; дополнительный режим реальных снимков с виртуальным условием описан внизу. Кошельков, подписей, RPC и отправки транзакций нет. Допуск к реальной торговле закрыт; поиск механизмов подписи и эксперименты безопасности остаются приостановленными. Стенд Swig находится отдельно в `../../experiments/swig-pump` и для этого прототипа не нужен.

**Браузерная панель:** `npm start` → **http://127.0.0.1:4173**. Полный сценарий создания, включения, передачи цены и просмотра сохранённого результата доступен без вызова внутренних функций. [Запуск, инструкция и ограничения](web/README.md).

Нужен Node.js >= 24.19 с `node:sqlite` (проверено на 24.19.0). Использованы только стандартные модули Node.js, без новых зависимостей и сервера БД. Установка пакетов не требуется. Из корня репозитория:

```sh
cd prototypes/rule-lifecycle
npm run demo
npm run demo:restart
npm run demo:source
npm run demo:owner
npm test
```

`demo` сохраняет прежнюю демонстрацию в памяти. `demo:restart` создаёт временное SQLite-хранилище, подтверждает создание/подготовку, останавливает процесс через **SIGKILL** и восстанавливает состояние новым процессом. Подготовленная операция исполняется отдельным явным запросом; ещё один перезапуск и повтор запроса дают ноль новых вызовов. Второй сценарий останавливается перед сохранением результата: восстановление даёт `unknown`, запрет включения и ноль новых вызовов. В конце временные файлы демонстрации удаляются.

`demo:source` показывает синтетический поток с устойчивыми ID, явной тестовой котировкой, разрывом, повторами и восстановлением в другом процессе. Курсор сохраняется атомарно с решением по событию и намерением операции. Потеря истории фиксирует `decision_required`; подключение транспорта не снимает запрет исполнения. [Контракт, порядок, API и требования к будущему провайдеру](EVENT_SOURCE.md). Это не проверенная интеграция с Solana.

`demo:owner` показывает явное решение по конкретному случаю нарушения: отзыв либо проверку восстановленной истории с отдельным включением и свежими данными. Принятие невосстановимого пропуска явно неподдерживаемо — недостаёт контракта новой точки отсчёта. `unknown` независимо запрещает повтор. [Команды, переходы, авторизация DEMO и атомарный журнал](OWNER_DECISIONS.md).

## Тестовое правило

Значения из `fixtures.mjs` выбраны исключительно для проверок, это не торговая стратегия и не реальные пороги:

| Поле | Тестовое значение и смысл |
| --- | --- |
| `id`, `assetId` | `demo-rule-1`, `DEMO:ASSET-A` — условный идентификатор, не mint |
| `condition` | `priceUnits <= 100`; демонстрационное событие содержит `95` |
| `amountUnits` | `10` условных единиц расходуемого актива |
| `maxTotalSpendUnits`, `maxFeeUnits` | `11` с учётом комиссии; отдельно комиссия не больше `1` |
| `minReceiveUnits`, `maxSlippageBps` | Минимальное получение `4`; максимальное синтетическое проскальзывание `50` базисных пунктов |
| `maxEventAgeMs` | Возраст события не больше `100` мс; события из будущего отклоняются |
| `expiresAtMs` | Логическое время создания + `1000` мс; на самой границе правило уже истекло |

Денежные величины — целые условные единицы без связи с SOL или курсом. Имитатор не строит рыночную котировку: результат задаётся сценарием. Проверка `minReceiveUnits` и поля проскальзывания не доказывает экономически выгодную цену.

Создание проверяет идентификаторы, допустимое условие, положительные безопасные целые суммы, непротиворечивые лимиты и будущий срок. Параметры копируются и замораживаются; редактирования правила в этом этапе нет. Создание само по себе не включает правило.

## Два независимых состояния

| Состояние правила | Переход / смысл |
| --- | --- |
| `draft` | Создано, не принимает события для исполнения; включение → `active` |
| `active` | Принимает подходящее свежее событие; резервирует одну операцию |
| `paused` | Новые операции запрещены; включение возможно только до первой передачи имитатору |
| `finished` | Единственная переданная попытка завершилась известным успехом **или неуспехом**; повтор запрещён |
| `expired` | Срок истёк; новых операций и включения нет |
| `revoked` | Окончательный отзыв из любого состояния; включение невозможно |

| Состояние операции | Переход / смысл |
| --- | --- |
| `prepared` | Условие сработало, слот зарезервирован; можно отменить до передачи |
| `submitted` | Сохранена отметка «передача имитатору могла произойти»; подтверждённого сохранённого результата ещё нет |
| `succeeded`, `failed`, `unknown` | Результат имитатора; повторная передача этой операции невозможна |
| `cancelled` | Отменена только подготовленная операция, до вызова имитатора |

Пауза отменяет `prepared`, но не `submitted`. После паузы до передачи можно явно включить правило и подать **новое** свежее событие. Старое событие не переигрывается. Отзыв и истечение срока также не отменяют ранее переданное исполнение. Его поздний результат сохраняется отдельно; правило остаётся `revoked` или `expired`. После обычной паузы поздний известный результат переводит правило в `finished`.

Консервативное решение для демонстрации: **не больше одной передачи имитатору на правило** в одной сохранённой истории. Известная неудача также завершает попытку. `unknown` или исключение имитатора дают операцию `unknown` и паузу с запретом повторного включения. При восстановлении неопределённость возможна даже без фактического вызова — это цена отказа от потенциального повтора. Автоматического повторения, ручного повторения этой попытки или механизма разрешения неизвестного результата нет. Это не утверждение окончательной политики стратегии.

Срок проверяется при восстановлении, обработке команд/событий, чтении состояния и перед передачей. `tick()` позволяет явно обновить состояния по времени. Фонового таймера нет; без вызовов отображаемое состояние само не обновляется, но передача после срока запрещена. Свежесть события повторно проверяется перед передачей, в том числе после записи на диск. Если процесс ещё достоверно знает, что `submit` не вызывался, а за время записи данные устарели или срок истёк, он сохраняет `cancelled` и снимает резерв попытки. Авария до сохранения этого факта оставляет консервативный `unknown`.

## Поток и повторные запросы

`RuleEngine.createRule` → `enable` → `handleEvent` выполняет полный поток до результата имитатора. Для проверки промежутка между получением события и исполнением доступны отдельно `receiveEvent` и `executePrepared`. `pause`, `revoke`, `tick`, `getRule` и `getOperation` обслуживают жизненный цикл и наблюдение.

Изменяющим командам нужен `requestId`. Повтор команды с тем же содержимым возвращает прежнее подтверждение; другое содержимое с тем же ключом даёт `IDEMPOTENCY_CONFLICT`. Подтверждение команды — не текущее состояние: для него есть методы чтения. Даже повтор старого включения не снимает паузу/отзыв/истечение.

Для команды исполнения сохраняются её отпечаток и ссылка на операцию, а не объект Promise. Повтор возвращает актуальный сохранённый исход этой операции (после аварии это может быть `unknown`). В одном живом процессе параллельные запросы разделяют один Promise.

Legacy-события дедуплицируются по `(ruleId, event.id)` с проверкой содержимого. Изменённое событие с тем же ID даёт `EVENT_ID_CONFLICT`. Игнорированные события тоже запоминаются: включение или возобновление требует нового события. Другой актив, устаревшее/будущее событие и невыполненное условие не вызывают имитатор. Резервирование и проверка перед передачей синхронны; параллельные запросы одного процесса разделяют одну ожидающую операцию. Для привязанных источников используются `(ruleId, sourceId, eventId)` и отдельный контракт выше; legacy-путь для таких правил закрыт.

## Устойчивый режим и граница передачи

`RuleEngine.initialize({ storagePath, ...options })` — отдельное явное создание **нового** файла; существующий файл не перезаписывается. Родительский каталог должен существовать. `RuleEngine.open({ storagePath, ...options })` открывает **только существующую** историю. Путь обязателен для обоих методов. Обычный `new RuleEngine()` без пути оставлен для прежних тестов и демонстрации в памяти; ошибки устойчивого режима никогда не переключают его в этот режим автоматически. `engine.close()` освобождает блокировку; пока есть ожидающий имитатор, обычное закрытие отклоняется. После ошибки хранилища закрыть остановленный движок можно.

Выбран **один SQLite-файл с полным снимком**: для маленького локального прототипа это проще нескольких таблиц и собственного файлового журнала. Снимок включает правила/конфигурации, состояния и связи операций, счётчик ID, отпечатки и подтверждения команд, отпечатки и решения по событиям, сроки, времена и результаты. Все эти записи изменяются одной транзакцией SQLite (`journal_mode=DELETE`, `synchronous=FULL`). Объекты Promise и тестовый счётчик вызовов не сохраняются. История пока не очищается; размер и стоимость записи растут вместе с ней.

| Граница | Что уже сохранено и что означает авария |
| --- | --- |
| Создание/включение/пауза/отзыв | Состояние и идемпотентность сохранены до возврата подтверждения |
| `prepared` | Намерение и исходное событие сохранены; `submit` ещё не разрешён. Само открытие истории ничего не отправляет |
| Перед `submit` | Атомарно сохранены `submitted`, резерв единственной попытки и ключ команды исполнения (если она явная). Только после COMMIT допускается вызов имитатора |
| Между этой записью и записью результата | При аварии восстановление сохраняет `unknown` и блокирует новую попытку; отличить отсутствие вызова от потери его результата нельзя |
| Результат | Исход и итоговое состояние правила сохраняются до успешного разрешения Promise вызывающему коду |

После открытия сначала проверяются формат/версия, контрольная сумма и связи записей. Каждый незавершённый `submitted` становится сохранённым `unknown`; правило приостанавливается, но сохраняет уже установленный `revoked` или `expired`. Затем проверяются сроки на момент восстановления: подготовленное отменяется, неизвестное не объявляется отменённым. Известные результаты и окончательные состояния не сбрасываются. Автоматической отправки при открытии нет.

Отсутствующий, пустой, повреждённый файл, неподдерживаемая версия и неверные связи — ошибка открытия, а не пустая история. Ошибка записи не даёт подтверждения и останавливает дальнейшие действия данного экземпляра. Замена/удаление открытого файла обнаруживается по его идентичности. Нет автоматического ремонта, очистки или создания нового файла при таких ошибках. Неудачный ответ при записи сам по себе не доказывает, что изменений нет: после восстановления нужно повторить тот же ключ запроса, а не выдавать новый.

Для одного и того же файла SQLite удерживает **эксклюзивную блокировку на всё время соединения**, не только записи. Случайный второй экземпляр получает `STORAGE_BUSY` до обработки событий. После SIGKILL блокировку снимает ОС, SQLite восстанавливает свой журнал; ручного удаления «зависшего lock-файла» не требуется. Это ограничение одним исполнителем, без координации нескольких рабочих процессов.

## Границы гарантий

Гарантии относятся к **одному и тому же исправному локальному хранилищу**, единственному владельцу блокировки и корректным операциям файловой системы/SQLite. Подтверждение выдаётся после COMMIT с FULL-синхронизацией; проверена остановка процесса, но не отключение питания, отказ диска или ложный ответ оборудования на fsync. Сетевые файловые системы, несколько хостов, копирование/перемещение открытого файла, доступ через альтернативные имена и обход блокировок не поддерживаются. Нельзя отдельно удалять SQLite-журнал открытой/аварийной базы.

**«Ровно одно исполнение» внешней операции не гарантируется.** Запись допуска и внешний вызов не являются одной транзакцией. Мы предпочитаем сохранить неопределённость и отказаться от возможного повтора; возможна потеря попытки, которая фактически не дошла до имитатора. Нет сверки неизвестного исхода или команды признать его неисполненным. Нет общей дедупликации разных правил/файлов. Удаление истории с последующим явным созданием новой, восстановление старой копии и произвольное редактирование владельцем файлов находятся вне гарантий. SHA-256 обнаруживает случайные изменения, но не аутентифицирует данные. Сроки зависят от часов процесса. Источника реальных данных и аутентификации владельца нет. Это не production-сервис.

`LIVE_TRADING_ALLOWED=false`, конструктор допускает только demo и имитатор; адаптера реальной торговли нет. Это граница прототипа, не неизменяемое разрешение в блокчейне. Имитатор проверяет только собственную синтетическую квитанцию. Владение средствами, ограниченная подпись, получатель, бюджет, запрет расширения полномочий, onchain-отзыв/срок и неизменяемость параметров реальной сделки этим этапом не подтверждены.

## Новый сценарий: виртуальная позиция

Явно выбирается в форме отдельно от разового условия: вход → открытая позиция → TP/SL или запрос закрытия → сохранённый модельный результат. Точные рациональные расчёты без комиссий/проскальзывания; реальное исполнение не подключено. Старые правила и история сохраняются, SQLite обновляется до v4. [Пошаговая инструкция, переходы, арифметика и проверки](web/VIRTUAL_POSITIONS.md).


Текущий дополнительный интерфейс: [обычный Telegram-бот одного владельца](web/TELEGRAM.md). Существующая SQLite автоматически мигрирует в v6; перед обновлением остановите сервер и сохраните резервную копию по HANDOFF.md.
