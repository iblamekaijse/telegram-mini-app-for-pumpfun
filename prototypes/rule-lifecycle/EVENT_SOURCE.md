# Контракт синтетического потока v1

Только локальный DEMO. Это спецификация и проверенный синтетический адаптер, не интеграция с Solana и не проверка реального провайдера. Данные и торговые пороги условные. Кошельков, подписей, RPC и транзакций нет.

## Запись и доставка

| Поле | Контракт |
| --- | --- |
| `version` | `1` — версия записи источника |
| `sourceId` | Устойчивая идентичность журнала, например `DEMO:price-feed-v1`; включает смысл потока/фильтра и его поколение |
| `eventId` | Уникальный внутри источника ID факта; неизменен при повторах |
| `position` | Непрерывная целая позиция `1, 2, 3…` внутри этого журнала; не номер попытки доставки и не слот Solana |
| `assetId` | Идентификатор базового актива, например `DEMO:ASSET-A` |
| `occurredAtMs` | Время возникновения по часам источника, целое число миллисекунд |
| `type` | В этой версии поддержан только `synthetic-price` |
| `payload.priceUnits` | Положительное безопасное целое значение цены |
| `payload.quoteAssetId` | Валюта котировки: `DEMO:QUOTE-A`, вымышленная, не USD/SOL |
| `payload.quoteDecimals` | Точность единицы котировки: в fixture `2`, допустимо `0…9` |
| `payload.unit` | Только `quote-atomic-per-whole-base`: минимальные единицы котировки за одну целую единицу базового актива |
| `receivedAtMs` | Не поле источника. Движок сам добавляет локальное время получения в конверт доставки |

В fixture `priceUnits=95`, `quoteDecimals=2` означает **0.95 DEMO:QUOTE-A за одну условную целую единицу DEMO:ASSET-A**. Порог `100` означает 1.00 той же тестовой котировки; это не реальная торговая рекомендация. Сравнение выполняется целыми числами, без преобразования через float. Валюта, точность и единица должны точно совпадать с `condition.priceBasis` правила; иначе сохраняется `ignored_incompatible_price`, исполнения нет. Имитатор не вычисляет результат обмена по этой цене. Проверка параметров исполнения не доказывает экономически выгодную цену.

Идентичность факта — `(sourceId, eventId)`, независимо от доставки. Один факт должен сохранять позицию и всё содержимое. `receivedAtMs` в отпечаток не входит: повтор может прийти позже. Сохраняются исходная запись, решение и время первого надёжно обработанного получения. Время каждого повтора возвращается вызывающему коду, но полного журнала всех попыток доставки пока нет.

## API и синтетический адаптер

Для нового потока создаётся `streamRule()` из `fixtures.mjs`, затем до включения вызывается `bindSource(ruleId, { sourceId }, { requestId })`. Привязка допускается только для черновика без операций и требует явного `condition.priceBasis`. В этом этапе одно правило имеет один источник и начальный курсор **0**; автоматического перехода к текущей вершине журнала нет. Legacy-правила без источника сохраняют прежнюю семантику. Их `receiveEvent` оставлен для старых fixtures; у привязанного правила этот путь заблокирован (`SOURCE_CONTRACT_REQUIRED`).

`SyntheticSource` содержит конечный детерминированный журнал из переданных fixtures:

- `connect({ afterPosition })` проверяет доступность всей требуемой истории и готовит выдачу после курсора;
- `next()` возвращает событие, `disconnected` или `end`;
- `disconnect()` и `disconnectAfter(n)` имитируют разрыв;
- `replayOnNextConnect(positions)` задаёт повторные доставки; намеренная выдача будущей позиции позволяет проверить нарушение порядка;
- `pruneBefore(position)` имитирует потерю истории; `connect` сообщает `history_unavailable`, если курсор ниже доступной границы или выше вершины журнала.

`SourceConsumer({ engine, ruleId, source }).drain()` соединяется с источником, обрабатывает события по одному и передаёт подготовленные операции только имитатору. За вызов обрабатывается не больше `maxEvents` (по умолчанию 100); при разрыве допускается не больше `maxReconnects` повторных подключений (по умолчанию 1). Это ограниченный локальный цикл, не фоновый сетевой сервис. `reconnect()` и `disconnect()` доступны отдельно. Состояние источника читается через `engine.getSourceState(ruleId)`.

## Курсор и запись

Курсор принадлежит подписке правила и означает **максимальную непрерывную позицию с сохранённым решением**, а не последнее полученное сообщение и не подтверждённую торговую операцию.

1. Адаптер получает запись; курсор в SQLite ещё прежний.
2. Движок проверяет идентичность, порядок, актив, единицы, время и правило.
3. **Один COMMIT снимка** сохраняет решение/дедупликацию, новый курсор, изменения правила и, если условие сработало, `prepared` с его ID.
4. Передача имитатору — отдельный следующий шаг с прежней устойчивой отметкой `submitted` перед вызовом. Результат — ещё одна запись.

Игнорирование старого события, другого актива, несовместимой цены, невыполненного условия или события выключенного правила тоже является надёжно обработанным решением и продвигает курсор. Такой факт повторно не оценивается после включения правила: нужно новое событие.

Авария до COMMIT оставляет прежний курсор: при доступной истории другой процесс получает событие снова. Авария после COMMIT сохраняет и курсор, и намерение. После подтверждения непрерывности новый consumer сначала обслуживает уже сохранённое `prepared`, даже если источник не повторяет этот факт. Свежесть и срок проверяются снова. Само открытие SQLite ничего не отправляет; состояние соединения не сохраняется, поэтому до нового handshake передача подготовленной операции запрещена.

Если передача могла произойти, а результат не сохранён, остаётся прежнее правило восстановления `unknown`. Повторы, новые события, переподключение и наличие полной истории эту блокировку не снимают. Курсор не является доказательством исполнения. «Ровно одно исполнение» внешней операции не гарантируется.

SQLite-снимок v3 содержит `streams`, записи источника в прежнем хранилище событий, случаи нарушений и журнал решений. Миграции v1/v2 сохраняют прежние правила, операции, ключи команд и блокировки. Неизвестные версии/повреждения остаются ошибкой открытия. Отдельного хранилища/БД нет; прежняя эксклюзивная блокировка и остановка после ошибки записи сохранены.

## Порядок и непрерывность

| Ситуация | Решение |
| --- | --- |
| Следующая позиция `cursor+1` | Проверить и сохранить решение; только затем продвинуть курсор |
| Известная старая позиция с тем же ID/содержимым | Дубль; вернуть прежнее решение, курсор не изменять, новую операцию не создавать |
| Будущая позиция с пропуском | Сохранить `position_gap`, остановить исполнение; не сортировать и не перепрыгивать пропуск |
| Изменение факта под прежним ID, повтор позиции с неизвестным ID | Сохранить конфликт/невозможность подтвердить повтор, остановить исполнение |
| Неверная версия/тип/единица/источник | `invalid_source_event`, без продвижения курсора |
| Новая непрерывная позиция с более старым временем подходящего актива/котировки | Сохранить `ignored_out_of_order`, продвинуть курсор, не запускать правило |
| Равное время возникновения | Допустимо; порядок задаёт позиция |
| Событие из будущего или старше `maxEventAgeMs` | Сохранить игнорирование; возраст считается от `occurredAtMs`, не от времени повтора |

Временная граница хранится для данного актива и совместимой котировки. Данные другого актива/котировки и будущие данные не поднимают её. Часы процесса и источник времени в этом DEMO доверенные; синхронизация часов и семантика времени реальной сети не проверены.

## Переподключение отдельно от разрешения исполнения

Соединение — оперативное `connected/disconnected`. Устойчивое состояние непрерывности — `continuous`, **`decision_required`** с ID случая/первой причиной/деталями/временем либо `stopped` после окончательного решения об отзыве. Состояние правила и исход операции остаются отдельными.

Недоступная история, пропуск позиции или конфликт идентичности сохраняют `decision_required`; активное правило приостанавливается, ещё не переданное намерение отменяется. Уже переданная операция не изображается отменённой. При ошибке хранилища состояние не подтверждается, экземпляр прекращает работу.

Переподключение может успешно восстановить транспорт и при этом оставить исполнение заблокированным. Повторное `enable`, новая доставка или последующее наличие полного журнала **не снимают** сохранённую блокировку. Автоматическое восстановление соединения также не включает правило, которое пользователь поставил на паузу.

**Сброса без проверки нет.** Добавлены [явные решения владельца по актуальному случаю](OWNER_DECISIONS.md): отзыв либо проверка полного восстановленного журнала. Успешная проверка не исполняет накопленные сигналы и не включает правило автоматически; новые сигналы должны возникнуть после решения. Принятие невосстановимого пропуска остаётся неподдерживаемым до отдельного контракта новой точки отсчёта. Нет кнопки объявить `unknown` неисполненным. Потеря истории не скрывается под успешным подключением.

## Что должен обеспечить будущий провайдер

- Устойчивые ID фактов и журналов, включая поколение и фильтр; отсутствие тихого сброса/переиспользования позиций. Идентификатор актива должен однозначно определять сеть и актив.
- Возобновление после сохранённого курсора с полным покрытием оставшихся позиций; повторная доставка допустима. Нужно явно обнаруживать утрату истории, а не незаметно переходить к новым данным.
- Документированные порядок, срок хранения, границы покрытия и backpressure. В данной реализации нет буфера перестановки; провайдер должен дать совместимый журнал или потребует отдельного согласования контракта.
- Определённое время факта и явные единицы/валюта/точность цены; проверяемое преобразование формата провайдера без сравнения разных размерностей. Время получения задаёт наш адаптер.
- Явная семантика финальности и исправлений/откатов. Этот контракт требует неизменяемых фактов: нельзя молча менять содержимое под прежним ID. Для реальной Solana нужно отдельно определить финальность или расширение контракта для пересмотров.

Эти свойства **не проверены у реального поставщика**. Последовательный счётчик синтетического журнала не доказывает полноту Solana RPC/WebSocket, потоков Pump.fun/PumpSwap или совместимость их курсоров. Реальное торговое исполнение и onchain-ограничения остаются неподтверждёнными.

## Запуск и доказательства

Из `prototypes/rule-lifecycle`: `npm run demo:source` и `npm test`. Новая демонстрация использует SQLite и отдельные процессы: разрыв → SIGKILL → повтор/автоматическое переподключение → восстановление, затем отдельный пример потери истории и сохранённой блокировки. Временные файлы в конце удаляются.

На этапе источника пройден **81 тест** (59 прежних, 22 новых); текущий набор и решения владельца описаны в [OWNER_DECISIONS.md](OWNER_DECISIONS.md). Проверки источника включают реальные остановки процессов до записи события, перед COMMIT и после него, согласованность курсора/намерения, повтор после рестарта, `unknown`, потерю истории, порядок времени после рестарта, несовместимые цены, конфликт ID, отказ записи и миграцию v1. Здесь «реальные» относятся к локальным процессам/SQLite; источник и исполнитель синтетические. Исторические журналы: `results/source-tests.tap`, `results/source-demo.log`.
