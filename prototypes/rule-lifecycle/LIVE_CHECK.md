# Один живой прогон локального приложения, Telegram и рынка

Инструмент включён в **main** через PR №4; временную ветку выбирать не нужно. Это дополнение после **v0.1.0-paper.1**, не изменение опубликованного тега. Рабочая модель приложения остаётся виртуальной, SQLite v7. Никаких кошельков, сделок, платных API или публичного сервера.

## Единственный путь обновления и запуска проверки

В уже настроенной WSL сначала **Ctrl+C** в окне `npm start`, дождитесь приглашения оболочки. Остановите также другие экземпляры этого бота на своих устройствах/серверах: другой потребитель Telegram может существовать вне этой SQLite; обнаруженный 409 приводит к остановке проверки, а не к обходу. Прежние успешные setup/getMe/ID/webhook не повторяйте. Завершённая привязка личного чата пока не подтверждена: блок ниже проверит её и предложит привязку только при отсутствии владельца. Владелец автоматически не выбирается и не меняется.

Из существующего checkout выполните один блок. SQLite, `.env` и прежняя ссылка на код сохраняются. Это установка инструмента ради первого живого прогона; обслуживание уже выпущенного приложения само по себе обновления не требует.

```bash
(
  set -e
  cd "$(git rev-parse --show-toplevel)"
  if [ -n "$(git status --porcelain)" ]; then
    echo "Есть локальные изменения: сохраните их; обновление остановлено без reset/clean."
    exit 1
  fi
  PAPER_CHECK_STAMP=$(date +%Y%m%d-%H%M%S)
  git branch "backup/before-live-check-$PAPER_CHECK_STAMP" HEAD
  cd prototypes/rule-lifecycle
  npm run backup -- --to "$HOME/pumpfun-backups/before-live-check-$PAPER_CHECK_STAMP"
  cd ../..
  git fetch origin refs/heads/main:refs/remotes/origin/main
  git switch --create "local/main-$PAPER_CHECK_STAMP" --track origin/main
  cd prototypes/rule-lifecycle
  PAPER_OWNER=$(node --input-type=module <<'JS'
import { settings } from './ops/config.mjs';
import { inspectDatabase } from './ops/storage.mjs';
try {
  const db = await inspectDatabase(settings().dbPath, { exclusive: true });
  try {
    const s = db.state;
    if (!s.telegram.owner) {
      const r = s.rules.find(([, r]) => !['finished', 'expired', 'revoked'].includes(r.state));
      const p = s.positions.find(([, p]) => p.status !== 'closed');
      const u = s.operations.find(([, o]) => o.status === 'unknown');
      if (r || p || u) throw new Error('Конфликт: ' + (u ? 'unknown ' + u[0] : p ? 'позиция ' + p[0] : 'правило ' + r[0]));
      if (s.telegram.pending || s.telegram.dialog || s.telegram.outbox.some(e => e.status === 'pending'))
        throw new Error('Конфликт: прежний pending update, диалог или очередь; состояние сохранено.');
    }
    console.log(s.telegram.owner ? 'linked' : 'needs-link');
  } finally { db.close(); }
} catch (e) { console.error(e.code || e.message); process.exitCode = 1; }
JS
  )
  PAPER_BIND_PID=
  stop_binding() {
    if [ -n "$PAPER_BIND_PID" ]; then
      kill -TERM "$PAPER_BIND_PID" 2>/dev/null || true
      wait "$PAPER_BIND_PID" || true
      PAPER_BIND_PID=
    fi
  }
  trap stop_binding EXIT
  trap 'exit 130' INT TERM
  if [ "$PAPER_OWNER" = needs-link ]; then
    node ops/start.mjs & PAPER_BIND_PID=$!
    echo "Личный чат ещё не привязан. Откройте локальную панель по напечатанному адресу."
    echo "Telegram → Получить код привязки; отправьте /start КОД в личный чат своего бота."
    read -r -p "Дождитесь ответа «Привязка подтверждена» и очереди 0 в панели; затем Enter: " </dev/tty
    stop_binding
  fi
  if npm run live:check; then
    echo "Просмотрите итоговое сообщение бота и report.json: status должен быть completed."
  else
    echo "Прогон не завершён. Сохраните код/причину отказа и последний этап; объекты не меняйте ради теста."
  fi
  read -r -p "После просмотра результата Enter вернёт обычный сервер (выход из него — Ctrl+C): " </dev/tty
  npm start
)
```

Сохраните прежний `DEMO_ENV_FILE`, если использовали нестандартную конфигурацию. Команда читает те же `.env`, `DEMO_DATA_DIR`, `DEMO_PORT`, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_ID`; унаследованные значения имеют прежний приоритет. Токен вводить или передавать в чат/аргументы не требуется. Нет npm install или повторного setup. Только при отсутствии привязки блок временно запускает тот же обычный сервер через `ops/start.mjs`, затем корректно останавливает и дожидается его завершения. Сам прогон запускает существующий `startPanel` и единственный polling; после просмотра результата блок возвращает обычный `npm start`. Doctor остаётся справкой при конкретной ошибке, не обязательным дополнительным взаимодействием.

## Действия в Telegram

Если владелец ещё не привязан, сначала отправьте **`/start КОД`** из локальной панели своему боту в личный чат и дождитесь подтверждения. Если панель показывает «Владелец привязан», этот шаг пропускается; кнопку отключения привязки не используйте. `OWNER_REQUIRED` означает, что этот шаг не завершён, а не неисправность приложения и не необходимость нового setup.

Когда бот отправит сообщение **«ПРОВЕРОЧНАЯ виртуальная позиция …»** с маркером `[papercheck-…:status]`, воспользуйтесь Telegram **«Ответить» именно на это сообщение** и отправьте **`/status`** один раз. Это единственная контрольная команда прогона (первичная привязка требуется отдельно только при её отсутствии), не кнопка «Текущее состояние» и не самостоятельное сообщение без reply. Ответ содержит текущее правило/позицию. После него инструмент автоматически запрашивает виртуальное закрытие, дожидается следующего пригодного снимка, запускает новый процесс Node с той же базой и проверяет результат. Оставьте WSL и интернет включёнными.

В конце просмотрите итоговое сообщение бота и статус `completed` в локальном отчёте. Сам факт просмотра человеком **не подтверждается программой**: `userSawResult` остаётся `unconfirmed`. Сообщите, что увидели результат, только если это действительно так. Полный пошаговый Telegram-диалог создания/подтверждения/включения этим прогоном не проверяется: создание, включение и запрос закрытия выполнены существующим локальным сервисом, `/status` проходит настоящий Telegram update/controller/outbox.

## Что именно выполняется

- Прежде чем запускать приложение, под короткой эксклюзивной блокировкой проверяются занятость, payload и целостность; история не изменяется. Нужна уже настроенная v7. Незавершённое пользовательское правило, открытая/ожидающая закрытия позиция, unknown, старый pending update/диалог или неотправленная прежняя очередь блокируют новый прогон. Объекты не отзываются и не закрываются ради проверки. Во время продолжения допустим собственный сохранённый `/status`; новое пользовательское правило останавливает продолжение.
- Проверяются локальный `/api/diagnostics`, путь выбранной SQLite, настоящий getMe, ID конфигурации/базы, отсутствие webhook. Worker не запускает getUpdates/send до проверки личности. Webhook не удаляется. Полностью исключить внешнего конкурирующего потребителя нельзя; 409 фиксируется как незавершённость, второй потребитель инструментом не создаётся.
- По умолчанию mint `HnXDnwTa68tRhLRZdJkVRLAeYrUkCYgFgDavtwD1pump`. Это публичный пример, **не торговая рекомендация и не обещание доступности пула**. До первого прогона можно выбрать другой поддерживаемый mint через `npm run live:check -- --mint ПУБЛИЧНЫЙ_MINT`; продолжение использует прежний mint и пул. Источник прежний: DEX Screener, Solana, индексируемый PumpSwap base-token/WSOL, `priceUsd`. Возраст цены у агрегатора неизвестен; время отчёта — время локального наблюдения, не slot/time биржевого события.
- Создаётся явно отличимое правило `web-papercheck-…`, **1 виртуальный USD**. Порог входа — **двойная цена первого пригодного снимка**, условие `<=`; TP 10000%, SL 99.99%, срок 30 минут. Это намеренно широкие проверочные условия; все фактические цены берутся исключительно из живого источника. Использование первого кешированного снимка для входа запрещено: нужен новый снимок после создания/включения. Если цена уже выше порога, вход не изображается успешным. Пул закреплён; подмена источника/цены и обход unknown не используются. Если сработал TP/SL раньше проверяемого ручного выхода, результат сохраняется и прогон считается незавершённым.
- Сохраняются вход, запрос закрытия, следующий новый пригодный снимок и точные рациональные расчёты без комиссий/проскальзывания. После нового процесса Node проверяются прежние rule/operation/position, неизменность результата и отсутствие новой отправки уже подтверждённых уведомлений входа/закрытия. Сохраняется хеш исходных пользовательских правил/истории; совпадение проверяется отдельно. Проверочные записи остаются в истории навсегда; отчёт/база не удаляются для повторного «красивого» успеха.

## Сроки, прерывание и продолжение

Каждое автоматическое ожидание ограничено **120 секундами**, ответ владельца — **180 секундами**, работа одного процесса — **10 минутами**. После контрольного нового процесса проверяется новый пригодный снимок и минимум 11.5 секунды работы. Рыночный интервал 10 секунд, свежесть локального наблюдения 45 секунд, provider/Telegram backoff и пять попыток отправки сохраняются. Рыночный cooldown/backoff сохраняется в отчёте и выдерживается до нового процесса/продолжения; при аварии посреди запроса используется консервативное ожидание 128 секунд (или больше при длительном Retry-After). При 429/сбое допустим исход `incomplete`; отсчёт не сокращает Retry-After. Вызовы API имеют прежние сетевые timeout. Ctrl+C корректно завершает worker и сохраняет состояние; при аварийном завершении следующий запуск восстанавливает SQLite и снимает только lock несуществующего процесса.

После прерывания/истечения срока выполните **из каталога приложения ту же `npm run live:check`** с той же конфигурацией. Создание, включение, закрытие и сообщения используют прежние постоянные ID; второй rule/operation не создаётся. Если `/status` уже принят и обработан, повторять его не надо. Завершённый прогон при повторном запуске просто показывает прежний отчёт. Если собственное правило истекло, было приостановлено/отозвано или попало в unknown, инструмент не возобновляет его принудительно; отчёт содержит фактическое состояние и причину. Не удаляйте отчёт/правило для обхода такого ограничения.

При незавершённом прогоне собственное проверочное правило может остаться активным, а позиция открытой/с запросом закрытия: это записано в `actual`. После завершения или отказа приложение **остановлено**; обычная работа — `npm start` (она возобновит обычную обработку сохранённых объектов). Не запускайте её параллельно с проверкой. При конфликте с пользовательскими объектами завершите проверку позже, когда вы сами закончите обычную работу с ними; прогон не предписывает закрывать их ради теста.

Telegram гарантирует здесь подтверждение API, не человеческое прочтение. Если ответ sendMessage потерян после принятия сервером, прежняя очередь может повторить уведомление; это не повтор виртуальной операции. Для уже подтверждённых `sent` перезапуск не делает новую отправку. При исчерпанных попытках очередь не сбрасывается автоматически.

## Локальный отчёт и границы подтверждения

Путь печатается в терминале: `DEMO_DATA_DIR/.paper-live-check/report.json` (обычно `.local-web/.paper-live-check/report.json`), права файла 600/каталога 700. Отчёт содержит этапы и UTC Unix timestamps в миллисекундах, публичные mint/pool/snapshot, rule/operation/position ID, исходы, PID до/после, коммит и хеши исполняемых файлов каждой попытки. `actual` показывает последнее прочитанное состояние, `lastFailure` — причину незавершённости. При отказе до начала прогона причина выводится в терминал без создания отчёта.

`entryNotification`, `statusPromptApiAccepted`, `statusReplyApiAccepted`, `closeNotification`, `resultMessageApiAccepted` означают **Telegram API принял отправку**. `ownerUpdateReceived` означает реальный update с точным reply на сообщение этого прогона, от уже подтверждённого владельца в его личном чате; `statusProcessed` — продвижение offset и сохранённый ответ controller. `virtualEntry`/`virtualClose` — виртуальный расчёт в SQLite. `userSawResult: unconfirmed` честно отделяет просмотр результата человеком. Ни getMe, ни `sent` не заменяют этот последний пункт.

Токен, `.env`, ID владельца/чата и текст переписки не записываются в отчёт передачи. Локальный отчёт содержит технические ID и хеш привязки, игнорируется Git и не предназначен для публикации целиком. Не добавляйте пользовательскую базу или локальный каталог отчёта в PR. Завершение означает `status: completed` **и** `evidenceMode: live`; просмотр человеком отдельно остаётся `unconfirmed`. При отказе сообщите код/причину, последний успешный этап и конфликтующий ruleId/positionId/operationId, если он показан. Не присылайте токен, .env, базу или переписку. До начала прогона отчёт может отсутствовать — тогда достаточно строки отказа. Незавершённость не требует отзывать/закрывать пользовательские объекты ради теста.

## Что выполнено агентом

В Cloud нет настоящего Telegram-токена и доступа к WSL. Реальный DEX Screener проверен двумя последовательными пригодными наблюдениями одного закреплённого пула с соблюдением 10-секундного интервала: [публичный отчёт](results/live-check-cloud-market.json). Это **только рынок из Cloud**, не WSL и не полный живой цикл.

Полный подготовленный сценарий проверен на тестовых Telegram/market транспортах, настоящих HTTP/SQLite и временных данных, включая новый процесс Node, прерывания, дубли updates, неверный reply/владельца/чат, недоступный рынок, ненаступившее условие, webhook/ID-конфликт, занятое приложение и защиту прежней истории. Тестовые цены нигде не смешиваются с живым отчётом. Конкретные результаты и хеши кода — [отчёт подготовки](results/live-check-preparation.json). Живые Telegram send/update, связка с WSL и просмотр человеком остаются неподтверждёнными до запуска описанного сценария пользователем.

Заключительный разбор PR №4 нашёл и исправил потерю рыночного cooldown при новом процессе; прежний дефект воспроизведён усиленной проверкой уже существующего сценария. Результаты заключительных проверок и привязка к коду — [отчёт разбора](results/live-check-final-review.json). Предыдущий отчёт подготовки относится к c807e899…; старые результаты не выдаются за новые прогоны.
