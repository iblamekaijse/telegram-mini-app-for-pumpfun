# Решения владельца по нарушению потока — только DEMO

Локальное демонстрационное ядро, SQLite, синтетический источник и имитатор. Нет реальной авторизации владельца, кошельков, подписей или отправки транзакций. Стратегия, тестовые торговые значения и учёт единственной попытки не изменены.

## Команды и переходы

Каждый случай получает устойчивый `issue.id`, например `source-incident-1`, привязанный к правилу. Счётчик общий для истории SQLite и сохраняется вместе с нарушением. Пока случай не разрешён, повторные сообщения об ошибке сохраняют его исходную идентичность. После разрешения новое нарушение получает другой ID.

Общие предусловия решения: доверенный DEMO-контекст с правом на это правило; существующий `ruleId`; актуальный `incidentId`; `decision_required`; корректный `requestId`. Для точного повтора ранее принятой команды возвращается прежнее подтверждение без повторного применения.

| Действие | Дополнительные условия | Изменение состояния | Журнал |
| --- | --- | --- | --- |
| `revoke` | Актуальное нарушение; допустимо и при `unknown`, истёкшем/завершённом правиле | Правило → `revoked`, поток → `stopped`; соединение снимается; уже переданная операция сохраняет свой исход | `rule_revoked`, случай, субъект, прежнее/итоговое состояние и курсор |
| `retry_history` | Синтетический источник должен предоставить полный неизменяемый журнал от 1 до зафиксированной вершины; он сверяется с сохранённым префиксом | При успехе поток → `continuous`; правило остаётся на паузе либо истекшим. Курсор и восстановленные записи сохраняются, требуется новое соединение и отдельное включение, если оно ещё допустимо | `history_verified` с проверенным диапазоном и временной границей |
| `retry_history`, история недоступна/конфликтует | Полная проверка не прошла | Блокировка и курсор остаются; терминальное правило также не возобновляется | `history_unavailable`, `verification_failed` либо `terminal_rule` |
| `accept_gap` | Явное `acknowledgeHistoryLoss: true` | **Не поддерживается текущим контрактом**; курсор, операции и блокировка не меняются | `gap_acceptance_unsupported` с указанием недостающего контракта |

Отсутствие полномочий, устаревший случай, другой смысл того же ключа и неверные параметры отклоняются до принятия решения; записи принятого решения для них нет. Ошибки: `DEMO_OWNER_AUTH_REQUIRED`, `STALE_SOURCE_INCIDENT`, `IDEMPOTENCY_CONFLICT`, `HISTORY_LOSS_ACK_REQUIRED`. Обычный legacy-`revoke` при актуальном нарушении требует использовать команду решения (`INCIDENT_DECISION_REQUIRED`).

`getSourceDecisionLog(ruleId)` возвращает сохранённые записи: requestId, правило/случай, действие, доверенный тестовый субъект, время, исходная проблема, результат, детали и состояния до/после. Прежние случаи остаются в журнале после появления новых. Это локальный журнал, не защищённый от администратора файлов.

## Использование API и доверие

Привилегированная часть локального тестового стенда создаёт контекст один раз на процесс:

```js
import { createTrustedDemoOwnerContext } from './demo-owner.mjs';

const ownerContext = createTrustedDemoOwnerContext({
  ruleIds: ['demo-rule-1'],
  principalId: 'DEMO:trusted-local-owner',
});
const incidentId = engine.getSourceState('demo-rule-1').issue.id;
const result = consumer.decideIssue(
  { incidentId, decision: 'retry_history' },
  { requestId: 'explicit-owner-retry-1', ownerContext },
);
```

Другие действия: `decision: 'revoke'` и `decision: 'accept_gap', acknowledgeHistoryLoss: true`. Прямой вариант — `engine.decideSourceIssue(ruleId, decision, { requestId, ownerContext, source })`; `source` требуется для проверки истории, а не для отзыва. Свойства `ownerId` в запросе недостаточно. Контексты проверяются по идентичности объекта в приватном WeakMap, с областью конкретных правил; JSON и копия объекта не проходят. После перезапуска доверенный bootstrap выдаёт новый контекст, история решений и идемпотентность остаются в SQLite.

**Граница доверия:** фабрика контекста доступна привилегированному коду стенда; это намеренный тестовый вход, не сервис авторизации. `trustedDemoOwner` в дочернем process-worker — настройка этого локального стенда, её нельзя принимать из внешнего запроса. Пользователь с контролем процесса/файлов уже контролирует весь DEMO. Остальные старые команды тоже остаются локальным доверенным API. Для продукта ещё нужны проверенная аутентификация, соответствие субъекта владельцу конкретного правила/средств и проверка полномочий на всех изменяющих входах. Ни Telegram ID, ни текстовый ownerId, ни этот контекст не доказывают владение кошельком.

## Что означает проверенное восстановление

`SyntheticSource.readRecoveryHistory()` возвращает клонированный конечный снимок полного журнала и вершину. Если начало уже удалено, ответ — `history_unavailable`. Ядро принимает только синтетический адаптер, проверяет источник, непрерывность позиций, устойчивость ID, структуру записей и **совпадение всех ранее обработанных фактов**, а не только наличие соединения. Это более строгое требование, чем обычное возобновление после курсора. Если доступен только хвост, разрешение не выдаётся.

Восстановленный хвост сохраняется с решением `ignored_history_recovery`. Он не создаёт операций, даже если содержит подходящие и ещё свежие цены. Восстановление данных не является разрешением исполнить торговые сигналы времени остановки. Сохраняются все прежние операции, правила/лимиты, уже израсходованная единственная попытка, события и ключи команд. Отменённое ранее намерение не оживает.

Успех сохраняет `freshAfterMs` — момент принятия решения. Для последующего сигнала необходимы новая непрерывная позиция после проверенной вершины и время возникновения **строго позже** этой границы; старая цена даёт `ignored_before_resolution` с надёжным продвижением курсора. Кроме того, остаются прежние проверки актива/размерности/порядка, возраста, будущего времени и срока правила. Нужны отдельное явное `enable` и новый handshake источника. Включение не гарантировано: `expired`, `revoked`, `finished` и ранее переданная попытка его запрещают.

**Две независимые блокировки:** успешная проверка может убрать проблему потока при операции `unknown`, но не меняет её статус, ID, параметры, результат и `submittedOperationId`. Правило остаётся заблокированным для повторной попытки (`ATTEMPT_ALREADY_SUBMITTED`). Принятие новой истории, повтор старого решения и даже окончательный отзыв не объявляют отправленную операцию отменённой/неисполненной. Команды разрешения `unknown` нет.

После восстановления новое нарушение получает новый случай. Повтор старого requestId возвращает старую квитанцию, **не состояние текущего правила**, и ничего не снимает. Новый requestId со старым incidentId отклоняется. Совпадение случая повторно проверяется после проверки истории перед её применением.

## Почему принять невосстановимый пропуск пока нельзя

Поле `head` в сообщении об утрате истории — диагностическая вершина, не подтверждённая новая точка отсчёта. Текущий контракт не выдаёт связанный с поколением/фильтром журнала проверяемый anchor с позицией и временной границей, после которого гарантированы только допустимые новые данные. `readRecoveryHistory()` помогает только при наличии всей истории; в противном случае он не создаёт anchor.

Прежде чем поддерживать `accept_gap`, нужен отдельный контракт получения/проверки такой точки и гарантии возобновления строго после неё, а также явная запись утраченного диапазона. Он должен сохранять прежние бюджеты/операции/идемпотентность и независимую блокировку `unknown`. Это отдельное принятие потери истории, **не** успешное восстановление. Сейчас даже явное согласие владельца только фиксируется как неподдерживаемое; подставить произвольный курсор нельзя. Доступные варианты — повтор проверки с действительно восстановленным журналом либо отзыв правила.

## Хранение и проверки

Снимок SQLite v3 содержит счётчик случаев и журнал решений. Миграции v1/v2 сохраняют старую историю; существующим v2-нарушениям присваиваются устойчивые ID без разблокировки. Для одной команды результат, ключ идемпотентности, журнал и все изменения состояния записываются **одним COMMIT**. Отклонённая/неподдерживаемая возможность не маскируется как разрешение исполнения. После ошибки записи экземпляр блокируется, автоматического обнуления нет.

Проверены **106 тестов**, включая 25 новых. Тесты завершают дочерний процесс SIGKILL до записи, **после UPDATE внутри открытой SQLite-транзакции до COMMIT**, а также после COMMIT до ответа — для всех трёх действий. В других процессах проверяются состояние, журнал и повтор команды. Проверены искусственный отказ записи, устаревшие/повторные команды, пересечение правил, авторизация, совпадение сохранённой истории, свежие данные, срок и независимость `unknown`. Это остановка процесса, не отключение питания и не аудит финансового исполнения.

Из `prototypes/rule-lifecycle`:

```sh
npm run demo:owner
npm test
```

Демонстрация: активное правило → потеря истории → `decision_required` → неподдерживаемое явное принятие пропуска → проверенное восстановление → отдельное включение → свежий сигнал. Дополнительно показаны восстановленный поток при сохраняющемся `unknown` и окончательный отзыв с тем же неизвестным исходом. SQLite используется несколькими последовательными процессами; временные файлы в конце удаляются. Журналы: `results/owner-tests.tap`, `results/owner-demo.log`.

Реальный поставщик/подтверждение финальности, промышленная авторизация, onchain-полномочия исполнения, разрешение неизвестного исхода и готовность к средствам этим этапом не подтверждены. Сохраняются ограничения одного локального файла, эксклюзивного экземпляра, доверенных часов и отсутствие гарантии «ровно одного исполнения» внешней операции. Поиск подписания и прежние эксперименты безопасности остаются приостановленными.
